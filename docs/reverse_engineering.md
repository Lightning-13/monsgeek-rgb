# Reverse Engineering Process

This document describes the reverse engineering process used to understand the RGB protocol implemented by the MonsGeek FUN60 Pro keyboard.

Rather than documenting only the final protocol, this file explains the investigation itself, including the tools used, discoveries made, dead ends encountered, and conclusions reached.

---

# Objective

The goal of this project was to communicate directly with the keyboard's RGB controller without relying on:

* MonsGeek's official software
* `iot_driver.exe`
* gRPC-Web communication
* Any proprietary SDK

The long-term objective was to determine whether the keyboard supported host-controlled per-key RGB suitable for projects such as OpenRGB or SignalRGB.

---

# Hardware

The investigated device was a MonsGeek FUN60 Pro Hall Effect keyboard.

Known hardware includes:

* RongYuan RY5088 module
* Artery AT32F405 microcontroller
* Panchip PAN1080 wireless controller
* Yichip-based USB wireless receiver

Testing was performed using both wired USB and the supplied 2.4 GHz receiver.

---

# Software Tools

The following tools were used throughout the investigation:

* Wireshark
* USBPcap
* Python
* hidapi
* Visual Studio Code
* Official MonsGeek software

USB traffic from the official software was captured and compared with packets generated manually through Python.

---

# Initial Investigation

The first objective was identifying the USB interface responsible for RGB control.

Multiple HID interfaces were exposed by the keyboard.

USB captures showed that all lighting communication occurred through:

* Interface 2 (`MI_02`)

This interface was then accessed directly using `hidapi`.

---

# Packet Analysis

Captured HID traffic revealed several recurring opcode families.

These included:

| Opcode | Purpose                                 |
| ------ | --------------------------------------- |
| `0x07` | Mode selection and effect configuration |
| `0x0C` | Custom Layer framebuffer writes         |
| `0x0D` | Built-in visualizer traffic             |
| `0xF7` | Busy/ready polling                      |

Each opcode was isolated and reproduced manually until identical behavior was achieved without the official software.

---

# Checksum Discovery

All observed packet families shared the same checksum algorithm.

After comparing many captures, the following formula consistently validated every packet:

```text
checksum = (255 - (sum(header_bytes) & 0xFF)) & 0xFF
```

Implementing this checksum allowed entirely new packets to be generated successfully.

---

# Device Communication

Direct communication was established using Python and `hidapi`.

The project successfully:

* Opened the correct HID interface
* Sent Feature Reports
* Read Feature Reports
* Reproduced packets generated by the official software

This eliminated any dependency on MonsGeek's software stack.

---

# Busy / Ready Handshake

Early framebuffer transfers occasionally failed.

USB captures revealed that the keyboard expected a busy/ready handshake between framebuffer chunks.

Successful communication required:

1. Sending a query packet (`0xF7`)
2. Reading the feature report
3. Waiting until the device reported Ready
4. Sending the next chunk

Polling without retransmitting the query returned stale state and prevented progress.

---

# Framebuffer Discovery

The Custom Layer consists of a framebuffer containing 378 bytes.

Investigation showed:

* 126 RGB slots
* 3 bytes per slot
* Only 61 active LED locations

The remaining entries appear to be unused padding.

---

# Per-Key RGB

Individual LED slots were modified to identify physical keys.

Two mappings were confirmed directly using before/after USB captures:

| LED | Key |
| --- | --- |
| 9   | A   |
| 40  | B   |

The remaining active LED slots were identified through experimentation but have not yet all been individually mapped to physical key names.

---

# Custom Picture Mode

Before framebuffer writes would persist, the keyboard had to be placed into Custom Picture mode.

This was achieved by sending the packet:

```text
07 0D 04 04 00 00 C8 C8 53
```

Once this packet was sent, uploaded framebuffer data remained visible instead of being immediately replaced by the keyboard's built-in effects.

The exact meaning of the final `C8 C8` bytes remains unknown.

---

# Live Streaming Investigation

A significant portion of the investigation focused on finding a RAM-backed streaming protocol suitable for high-frame-rate per-key RGB animation.

Several possibilities were explored, including:

* Continuous framebuffer writes
* Alternative opcode values
* Built-in visualizer traffic
* Different operating modes
* Wired versus wireless behavior

No general-purpose RGB streaming protocol was identified.

---

# Audio Visualizer

One opcode (`0x0D`) initially appeared promising because it transferred data continuously at approximately 50 Hz.

Further analysis showed that these packets carried compact intensity values rather than RGB colors.

The keyboard firmware generated the animation internally using those values.

This channel cannot be used for arbitrary per-key RGB output.

---

# Flash-Based Custom Layers

Framebuffer uploads performed through opcode `0x0C` write to persistent onboard storage.

Evidence supporting this conclusion includes:

* Colors remain after reconnecting the keyboard.
* The official software updates the keyboard only after "Save to Layer" is pressed.
* Continuous high-frequency writes resulted in visible instability, consistent with repeated flash programming rather than RAM updates.

For this reason, framebuffer uploads should be treated as configuration changes rather than animation frames.

---

# Final Outcome

The reverse engineering effort successfully achieved:

* Direct HID communication
* Full protocol documentation
* Static RGB control
* Persistent per-key RGB layouts
* Wired and 2.4 GHz compatibility
* Open Python implementation

No evidence of a host-driven high-frame-rate RGB streaming protocol was found during this investigation.

---

# Future Work

Possible future areas of investigation include:

* Mapping every remaining LED index to a physical key.
* Comparing additional MonsGeek or Yichip keyboards.
* Firmware analysis of the AT32F405 microcontroller.
* Monitoring future MonsGeek software releases for protocol changes.
* Investigating undocumented firmware functionality if new evidence becomes available.

---

# Conclusion

This project demonstrates that the MonsGeek FUN60 Pro's RGB lighting can be controlled entirely through documented USB HID Feature Reports without relying on proprietary software.

The resulting protocol specification and reference implementation provide a foundation for future tooling, research, and support for compatible devices.
